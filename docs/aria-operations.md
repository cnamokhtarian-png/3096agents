# راه‌اندازی آریا برای Tabdeal Spot

این راهنما دستور عملیاتی است، نه گواهی فعال‌بودن محیط تولید. اجرای تست محلی
هیچ سفارش واقعی نمی‌فرستد. مستند مرجع: https://docs.tabdeal.org/

## پیش‌نیاز و فعال‌سازی

1. از دیتابیس نسخه پشتیبان بگیرید. روی دیتابیس دارای schema پایه، مهاجرت‌های
   زیر را به ترتیب اعمال کنید (اعمال مجدد کورکورانه نکنید):
   - `20261108_live_trade_positions.sql`
   - `20261109_trade_ledger_numeric.sql`
   - `20261110_trade_entry_fills.sql`
2. نقش اتصال برنامه باید مجوز دسترسی به جداول چرخه، ledger و اجرای چهار تابع
   `record_tabdeal_entry_fill`, `finalize_tabdeal_entry`,
   `record_tabdeal_exit_fill`, `finalize_tabdeal_exit_attempt` را داشته باشد.
   توابع با حقوق caller اجرا می‌شوند؛ مجوز PUBLIC باز نکنید.
3. کلید API تبدیل با دسترسی مشاهده و معامله و **بدون برداشت** را در تنظیمات
   امن صرافی ذخیره کنید. کلیدها را در گیت، چت یا URL قرار ندهید.
4. `EXCHANGE_NAME=tabdeal`، `CRON_SECRET` تصادفی و
   `TRADE_LIFECYCLE_ENABLED=true` را در محیط سرور تنظیم کنید.
   سپس قفل `AGENT_TRADING_ENABLED` را آگاهانه فعال کنید.
   تنظیمات ذخیره‌شده پنل نیز در انتخاب کلید و قفل معامله دخیل هستند.
   **تبدیل testnet ندارد**؛ `EXCHANGE_TESTNET=true` آن را شبیه‌سازی نمی‌کند.
5. زمان‌بند خارجی هر دقیقه درخواست زیر را به دامنه واقعی برنامه بفرستد:
   `GET /api/cron/tick?job=aria`
   با هدر `Authorization: Bearer <CRON_SECRET>`.
   توکن را در query string نگذارید. کرون روزانه موجود جایگزین پایش دقیقه‌ای نیست.
6. پاسخ `ok=true` و ثبت منظم `cron_runs` با job=`aria` را بررسی کنید.
   برای HTTP 503، timeout و قطع heartbeat بیش از دو دقیقه هشدار بیرونی بگذارید.
   خود برنامه نمی‌تواند هنگام قطعی کامل سرور هشدار قابل اتکا بفرستد.
7. نخست با بودجه محدود، پیشنهاد BUY LIMIT کامل را در پنل ایجاد و جداگانه تأیید
   کنید؛ ورود بدون تأیید انسانی انجام نمی‌شود. نتیجه واقعی ورود، خروج، کارمزد
   و مانده حساب را با صرافی تطبیق دهید؛ صرف HTTP 200 کافی نیست.

## چرخه

آریا ورودها را تطبیق می‌دهد، خروج‌های قبلی را بازیابی می‌کند، حد سود/ضرر
پوزیشن‌های تأییدشده را با قیمت bid تازه بررسی می‌کند، فروش MARKET با مقدار
ارز پایه می‌فرستد، fillها را با توابع اتمیک ثبت و گزارش بسته‌شدن را ارسال می‌کند.
خرابی یک مرحله مانع تلاش مراحل دیگر نمی‌شود؛ نتیجه نهایی در این حالت 503 است.
هر مرحله batch محدود دارد؛ با افزایش تعداد پوزیشن‌ها تأخیر واقعی را اندازه بگیرید.

شناسه سفارش قبل از تماس شبکه ذخیره می‌شود. پاسخ گم‌شده با همان clientOrderId
استعلام می‌شود، نه با ارسال دوباره سفارش. fill با کلید exchange/symbol/trade_id
یکتاست. برای رفع وضعیت unknown، ردیف attempt را حذف یا reset نکنید.

کارمزد ارز سوم در دفتر دارایی همان ارز ثبت می‌شود. تا ارزش‌گذاری معتبر،
`has_unvalued_fees` یعنی سود خالص نهایی دلاری معلوم نیست؛ مقدار تخمینی نسازید.
باقی‌مانده کمتر از حداقل بازار و سفارش نامعلوم نیازمند رسیدگی‌اند، نه بستن صوری.

## توقف و محدودیت‌ها

`TRADE_LIFECYCLE_ENABLED=false` ورود جدید را می‌بندد، ولی endpoint اختصاصی آریا
می‌تواند پوزیشن‌های قبلاً تأییدشده را مدیریت کند. خاموش‌کردن قفل عمومی معامله،
فروش و لغو سفارش را هم مسدود می‌کند؛ پیش از آن ریسک پوزیشن باز را مدیریت کنید.
`job=trade_reconcile` برای بازیابی و ثبت بدون ارسال فروش جدید موجود است، ولی
ممکن است سفارش باز قدیمی را لغو کند.

حد سود/ضرر نرم‌افزاری تضمین قیمت یا اجرا نیست: قطعی سرور، تأخیر زمان‌بند،
لغزش بازار و محدودیت API می‌توانند زیان را از حد تعیین‌شده بیشتر کنند.
این پیاده‌سازی Spot با مظنه USDT است، نه اهرم/FAPI و نه همه بازارهای تومانی.

## آزمون

`npm run verify:trade` تست‌ها، typecheck، lint و build آفلاین را اجرا می‌کند.
این فرمان اتصال تولید، اعمال مهاجرت، دسترسی API و سلامت زمان‌بند را تأیید نمی‌کند.

## شبیه‌سازی کاملاً آفلاین (بدون کلید و Supabase)

```sh
npm ci
npm run aria:dry-run
# تکرار اختیاری، بین ۱ تا ۲۰ بار؛ ممکن است چند دقیقه طول بکشد:
npm run aria:dry-run -- 3
```

این فرمان مجموعه سناریوهای موجود ورود، پایش، تطبیق، اجرای جزئی، timeout،
ثبت تکراری، rollback، توازن لجر و کارمزد را با PGlite موقت اجرا می‌کند.
متغیرهای حساس محیط به پردازش تست منتقل نمی‌شوند و ارتباط شبکه توسط guard
مسدود است. نیازی به کلید، تغییر قفل معامله، مهاجرت Supabase یا زمان‌بند ندارید.

گزارش قابل بازتولید در `reports/aria-dry-run/summary.json` و لاگ‌های TAP کنار آن
ذخیره می‌شوند و در گیت ثبت نمی‌شوند. خروج ناموفق فرمان یعنی حداقل یک سناریو
یا اجرای تست شکست خورده؛ برای تشخیص، لاگ همان اجرا را بررسی کنید.

این تست رگرسیون قطعی است، نه بک‌تست استراتژی یا Paper Trading با بازار زنده.
اعداد و نمادهای fixture متنوع‌اند؛ این فرمان معامله فرضی مشخص ETHUSDT با بودجه
۱٫۸ تتر را اثبات نمی‌کند. تکرار تست ثابت، شواهد آماری سودآوری تولید نمی‌کند.
حتی همه تست‌های موفق هم جای بررسی محدودیت بازار، مجوزهای تولید و تست زمان‌بند
را نمی‌گیرند. برای تست آفلاین، endpoint واقعی `job=aria` را صدا نزنید؛ آن مسیر
به وابستگی‌های واقعی متصل می‌شود.

## Paper Trading با قیمت عمومی بازار (مسیر جدید و مستقل)

این قابلیت در کد آماده شده؛ تا استقرار، اعمال مهاجرت و تنظیم زمان‌بند، فعال نیست.
برای این مسیر نیازی به کلید صرافی یا فعال‌کردن معاملات واقعی نیست.

1. مهاجرت مستقل `20261111_paper_monitor.sql` را در محیط موردنظر اعمال کنید.
   نقش برنامه باید روی دو جدول `paper_monitor_*` و sequence مربوطه دسترسی داشته
   باشد. RLS روشن است و سیاست عمومی ندارد؛ نقش مجاز باید آگاهانه انتخاب شود.
2. `PAPER_MONITOR_ENABLED=true` و `CRON_SECRET` امن را تنظیم و نسخه را مستقر کنید.
   برای ایزولاسیون کامل از عملیات واقعی، پروژه استقرار آزمایشی باید بدون کلید
   صرافی باشد و زمان‌بندهای full/fleet/queue/aria آن غیرفعال باشند. خاموش‌کردن
   env به‌تنهایی قفل تنظیم‌شده در دیتابیس را الزاماً خنثی نمی‌کند.
3. مدیر واردشده به پنل می‌تواند به `/api/paper/tick` درخواست POST بفرستد، مثلاً:

```json
{"symbol":"ETHUSDT","budget":"1.8","stop":"PRICE_BELOW_CURRENT_ASK","target":"PRICE_ABOVE_CURRENT_ASK","feeBps":"10","slippageBps":"20"}
```

قیمت‌های stop و target را بر اساس قیمت همان لحظه با رشته اعشاری واقعی جایگزین
کنید. ارقام هزینه بالا فقط فرض آزمایش‌اند، نه نرخ تأییدشده تبدیل. ۱۰ واحد پایه
یعنی ۰٫۱ درصد. اولین tick خرید فرضی، tickهای بعدی نگهداری یا خروج فرضی هستند.
4. زمان‌بند خارجی هر دقیقه فقط `GET /api/paper/tick` را با هدر Bearer صدا بزند.
   مسیرهای `job=aria` و `job=full` را برای این آزمایش استفاده نکنید.
5. نتایج در `agentos.paper_monitor_sessions` و مشاهدات/خطاها در
   `agentos.paper_monitor_ticks` ثبت می‌شوند. این جداول به لجر و دارایی واقعی
   مرتبط نیستند. تیک هم‌زمان با revision کنترل می‌شود. سقف هر اجرا دو جلسه است.

مدل از bid/ask عمومی تبدیل استفاده می‌کند و قیمت کهنه، پاسخ نامعتبر و خطای API
را با عدد ساختگی جایگزین نمی‌کند. زمان freshness بر اساس شروع درخواست است، نه
تضمین timestamp صرافی. هزینه و PnL با محاسبه اعشاری و گردکردن مشخص محاسبه می‌شوند.

**محدودیت:** این مدل اجرای فرضی با کارمزد USDT است؛ عمق کافی، صف سفارش، محدودیت
حداقل سفارش، lot size، partial fill واقعی و هزینه ارز سوم را مدل نمی‌کند.
بنابراین سود کاغذی یا امکان خرید فرضی ۱٫۸ تتری اثبات امکان اجرای واقعی نیست.
این مسیر استراتژی تولید نمی‌کند؛ سناریوی ورود و حدها توسط کاربر تعریف می‌شوند.

## وضعیت آماده‌سازی و کرون مستقل (بازبینی نهایی)

- مهاجرت‌های لجر NUMERIC و ثبت اجراهای خرید/فروش روی Supabase اعمال شدند.
- مبلغ‌های لجر USDT دارای NUMERIC(20,8) هستند. مقدار ارز پایه، قیمت و کارمزد
  ارزهای دیگر عمداً NUMERIC دقیق بدون محدودیت ۸ رقم باقی می‌مانند؛ تحمیل ۸ رقم
  به توکن‌های ریز می‌تواند دارایی را گرد یا صفر کند.
- نقش `agentos` برای چهار تابع و جداول لازم مجوز صریح دارد؛ دسترسی عمومی باز نشده.
- قبل از مهاجرت، تصویر داده و تعریف ستون‌های سه جدول موجود در اسکیمای خصوصی
  `aria_recovery_20261108` ذخیره شد. این snapshot داخل همان دیتابیس است، نه
  بکاپ مستقل disaster recovery. هر سه جدول در زمان بررسی خالی بودند.
- کرون خارجی `aria-minute` در Supabase pg_cron از Vault و pg_net استفاده می‌کند؛
  token در متن cron یا فایل گیت ذخیره نمی‌شود. درخواست فقط `job=aria` است.
- `ARIA_EXECUTION_MODE=observe` به‌صورت پیش‌فرض فقط شمارش وضعیت و heartbeat ثبت
  می‌کند و هیچ API امضاشده‌ای را صدا نمی‌زند. این حالت با Paper Trading متفاوت است.
- برای ورود جدید هم حالت live و هم `TRADE_LIFECYCLE_ENABLED=true` و تأیید مستقل
  هر معامله لازم‌اند. استقرار کد به‌خودی‌خود مجوز معامله واقعی نیست.
- شکست آزمون SET ROLE در کانکتور به معنی موفقیت تست نقش واقعی نیست؛ مجوزها از
  کاتالوگ بررسی شده‌اند و آزمون حسابداری همان نقش باید با اتصال واقعی برنامه
  انجام شود. شناسه یا داده فرضی تولید برای دورزدن این محدودیت وارد نشده است.

## هماهنگی پنل و تلگرام

فرم دفتر آریا اکنون فقط BUY/LIMIT نقدی با مقدار ارز پایه، قیمت ورود، سقف بودجه،
حد ضرر و حد سود می‌سازد. مقدارها رشته اعشاری‌اند و جمع هزینه بدون Number محاسبه
می‌شود. سقف بودجه، ارزش خرید پیش از کارمزد است و تضمین سقف کل با کارمزد نیست.
پیش‌نمایش پنل، متن صف و خلاصه تلگرام از یک قرارداد مشترک استفاده می‌کنند.
درخواست ناقص، اهرمی، SELL یا MARKET پیش از ایجاد job و ارسال پیام رد می‌شود.
API پنل پیش از ثبت، فیلترهای عمومی بازار را هم بررسی می‌کند؛ خطای این بررسی
هیچ کارت تازه‌ای ایجاد نمی‌کند. تمام مسیرهای ساخت job نیز اعتبار ساختاری را
پیش از ذخیره بررسی می‌کنند. آماده‌بودن ساختار با آماده‌بودن اجرای واقعی متفاوت است.

کارت‌های قدیمی تلگرام به‌صورت گذشته‌نگر ویرایش نشده‌اند؛ ردشان کنید و پس از
به‌روزرسانی پنل، درخواست تازه بسازید. تأیید کارت قدیمی هم دوباره preflight
سرور را طی می‌کند و درخواست نامعتبر نباید به اجرا برسد. این تغییر قفل observe
یا مجوزهای مالی را روشن نمی‌کند و هیچ درخواست واقعی به‌صورت خودکار نمی‌سازد.
